# Native authoring application validation — 2026-11-11

## Change and practical scope

Jason Stys's original deterministic PDF pipeline and cited corpus comparator now power a genuine
local authoring application. Users upload their PDFs, declare source/revision/permission metadata,
edit bounded settings, validate fields separately from processing, save exact revisions, build with
the original engine, inspect cited content/findings, preview/download exact artifacts and compare
actual saved corpora. Complete project files carry actual source bytes; imports create new project
identities and never adopt supplied output claims. Immutable results survive later edits/restarts.

The added native owner controls workspace Open, browser access, Help and normal Exit. The app
reserves its own ephemeral loopback listener and keeps ownership until accepted transport work
and actual PDF child processes finish. It uses one trusted OS owner's local plaintext workspace.
The original CLI, canonical contracts, publication gate, deterministic artifacts and corpus
comparison implementation remain intact; only the product version changes in that core package.

## Dependency and packaging boundary

The native archive excludes PyMuPDF, fitz and MuPDF binaries. Before opening any profile, document
or listener, a real Install/Cancel dialog describes the exact official wheel and upstream
AGPL/commercial terms. A separate explicit console setup path exercises the same actual installer.
The wheel's full size/digest, ABI, metadata, RECORD, bounded extraction and exact offline byte/tree
inventory must verify before import. No user document is sent to its provider. See
[the detailed technical/licensing boundary](../PDF_ENGINE_SETUP.md).

Packaging uses a **new minimal full-hash-locked environment**, not the developer environment's
optional test dependencies. Runtime and pinned PyInstaller-compatibility graph terms are collected
from that actual environment. The real frozen module/tree inventory independently refuses parser
payloads and unreviewed developer modules. Loaded Tcl/Tk library notices use actual bytes or a
narrowly version/source-bound reviewed distribution notice; no family-based substitute is made.

The first clean minimal Windows archive exposed a real missing dependency before the app opened:
the externally installed parser uses CPython's stable-ABI `python3.dll`, which was absent because
the parser is intentionally not frozen. Packaging now explicitly collects that DLL from the same
patched SDK, binds its actual SHA-256 in metadata and verifies it again before document access.
The ordinary `python314.dll` retains its independent identity check. Four missing/substituted-DLL
oracles exercise both paths. No parser binary was added to the app. The preserved failed setup is
not reported as a successful package. Windows also needs Microsoft's supported Visual C++ runtime
for the official parser wheel; this work does not claim a dependency-free clean-machine install.

## Failures preserved and corrections

Actual early tests exposed upstream buffered stdout contaminating the worker JSON protocol.
The fixed launcher separates diagnostics before importing the parser, retains those diagnostics
and keeps protocol bytes on their original descriptor. A real child failure also exposed a Windows
pipe-close error; close/read failures are now collected and refuse the job.

Harness corrections were separately identified: an initial one-page expectation contradicted the
original two-page fixture; a revised PDF used unsupported notice labels and was correctly blocked;
an immediate filtered-DOM count sampled the old render; and Axe required an explicit browser
context. None justified changing the original engine, weakening an oracle or retrying a failed
application operation. Native setup also exposed a very long **test** dependency path exceeding
the Windows extension loader limit; a new short owned OS-temp directory models normal per-user
setup and preserves the failed evidence. The documented normal dependency path remains separate
from source checkout and workspace paths.

Additional review fixed truthful source-count wording, empty-list semantics and empty preview
presentation. A packaging inventory caught optional developer libraries; the minimal build
environment and exact component notice graph address that source of nondeterministic payloads.

The owner now binds the canonical dependency location **after** verified setup, rather than keeping
the earlier environment snapshot. This matters for a Linux custom XDG data directory: the actual
worker must use the already verified installation. A real-service regression covers that boundary;
native consumers exercise ordinary OS-derived paths in isolated process environments.

One later whole-suite run preserved a Windows `WinError 10053` in an invalid-URL negative: sending
a full body raced the server's correct pre-body rejection/close. That fixture now sends authenticated
headers with `Expect: 100-continue` and requires an actual complete **400** response before any body,
without accepting a reset, changing the status/deadline, reading untrusted data or retrying the case.

The first hosted PR run preserved additional failures rather than passing them off as product
success. All three original source versions stopped at collection: the console `pytest` entrypoint

## Required clean/hosted gate and reproduction

Run from a clean checkout, with the supported toolchain and the exact locked browser installed:

```bash
python -m pip install --require-hashes -r requirements-dev.lock -r requirements-package.lock
python -m pip install --no-deps --no-build-isolation -e .
npm --prefix web ci --ignore-scripts
npm --prefix web test
npm --prefix web run smoke
ruff format --check .
ruff check .
mypy src
pytest --cov --cov-branch --cov-report=term-missing
python -m build --no-isolation
pip-audit
npm --prefix web exec -- playwright install chromium
npm --prefix web run check:browser-host
python -m tools.package_app --output-root .runtime/new-clean-native-check
```

On headless Linux, use `xvfb-run -a` for Tk tests and native packaging. Source CI preserves Python
3.11/3.12/3.13, tests both packages at the original coverage floor, builds distributions and audits
dependencies. Native CI uses patched Python 3.14.10 on Windows, Linux and macOS, builds an archive,
safely extracts it and executes only that actual app. It exercises explicit setup, real browser
flows, exact source/version/nonce identity, accepted publication drain, restart retention and normal
exit/listener closure. It has no release authority and uploads no full binary artifact by default.

Hosted status is recorded by the exact-source [native workflow](../../.github/workflows/desktop.yml),
[source CI](../../.github/workflows/ci.yml) and [CodeQL](../../.github/workflows/codeql.yml), rather than
invented from local tests. No public 0.2.0 release, independent PC installation, signed package,
first-run OS transaction, every-browser acceptance or full-main zero-alert scan is asserted here.

## Limits

This application supports bounded text PDFs and ruled tables, with image placeholders and
heuristic headings. It supplies no OCR, universal document understanding, automatic unit conversion,
technical truth validation or engineering/safety approval. Source rights are declared by the user.
The local plaintext workspace is not a multiuser service, hostile-PDF sandbox or defense against
a hostile process already running as the same OS user. Exports can contain source content and
diagnostics; review them before sharing. Bootstrap is a technical distribution mechanism, not a
licensing-clearance or commercial-license claim. Portable unsigned archives need matching OS/CPU;
normal OS restrictions remain. Manual desktop/OS-browser and public release acceptance are separate.
